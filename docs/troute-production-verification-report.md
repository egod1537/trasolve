# troute 배포 서버 실사용 일정 검증 보고서

## 요약

2026-11-12에 배포된 `troute` 서버에 실사용자 여행기 기반 하루 일정 100건을
직접 전송했다. 검증 요청 100건과 최적화 Job 100건이 모두 성공했고, 모든
최적화 결과가 로컬 기준 결과와 경로 순서 및 총 이동 시간까지 일치했다.

따라서 이 데이터셋이 제공하는 운영 시간, 체류 시간, 시작 시간 및 이동 시간
행렬을 전제로 할 때, 배포 서버는 실행 가능한 서울·몽골 하루 일정을 정상적으로
검증하고 최적해를 반환한다.

## 검증 대상

- 서버: `https://troute.mangagaki.net/api/`
- 실행일: 2026-11-12 (Asia/Seoul)
- 데이터셋: [`data/troute-real-user-itineraries-100.json`](data/troute-real-user-itineraries-100.json)
- 데이터셋 설명: [`troute-user-itinerary-dataset.md`](troute-user-itinerary-dataset.md)
- 전체 실행 Job 접두사: `ru26-mwcxu7nb-*`

서버의 `/health` 응답이 HTTP 200과 `{"status":"ok"}`를 반환하는 것을 확인한
후 검증을 시작했다.

## 데이터셋 구성

| 항목 | 값 |
| --- | ---: |
| 전체 테스트셋 | 100건 |
| 서울 | 50건 |
| 몽골 | 50건 |
| 기본 일정 템플릿 | 20개 |
| 템플릿당 변형 | 5개 |
| 전체 정류장 | 540개 |
| 테스트셋당 정류장 | 4~7개, 평균 5.4개 |

각 정류장에는 `open_time`, `close_time`, `stay_minutes`를 제공했다. 요청에는
`start_policy=FIXED`, `start_time`, 이동 수단, 국가 코드 및 완전한
`travel_time_matrix`가 포함된다. 서울은 `TRANSIT`, 몽골은 `DRIVING`으로
구성했다.

운영 시간은 공개 자료와 일반적인 운영 시간대를 바탕으로 구성했으며, 해가
존재하도록 일부 종료 시간을 확장했다. 따라서 실제 당일의 임시 휴무, 계절별
운영 시간 변경까지 보증하는 데이터는 아니다.

## 실행 방법

전체 테스트는 동시에 최대 5건만 처리하도록 제한하고 다음 순서로 수행했다.

1. `POST /validate`에 `route`와 알려진 실행 가능 시각인
   `service_start_times`를 전송한다.
2. 응답의 `input_valid`, `schedule_feasible`, `blocks_optimization`을 확인한다.
3. `POST /integration/jobs`에 동일한 최적화 요청을 제출한다.
4. `GET /integration/jobs/{job_id}`를 완료 상태까지 조회한다.
5. 배포 서버 결과와 데이터셋에 기록된 로컬 기준 결과를 비교한다.

비교 항목은 최종 상태, 최적 경로의 location ID 순서, 총 이동 시간 및 최적성
증명 상태다.

### 최적화 동작

| 항목 | 결과 |

| 입력 순서와 다른 최적 경로 | 44/100 |
| 입력 순서보다 이동 시간이 짧아진 경로 | 26/100 |
| 단축된 경로의 평균 절감 시간 | 4.6분 |

입력 일정 자체가 실제 여행기에서 추출한 지리적으로 자연스러운 순서이므로,
나머지 케이스는 입력 순서가 이미 최적이거나 동일한 목적값을 갖는 순서가
존재했다. 순서가 변경된 44건 중 일부는 총 이동 시간이 같은 동률 최적해다.

## 해석

이번 결과는 다음을 확인한다.

- 배포된 API의 검증 및 비동기 Job 계약이 현재 데이터셋과 호환된다.
- 제공된 시간창과 이동 시간 안에서 100개 일정 모두 실행 가능한 해가 있다.
- 모든 케이스가 exact solver에서 `OPTIMAL`로 종료됐다.
- 로컬과 배포 환경의 최적 경로 및 총 이동 시간이 결정적으로 재현된다.
- 서울의 대중교통형 일정과 몽골의 장거리 운전형 일정 모두 동일하게 통과한다.

## 보장하지 않는 범위

이번 검증은 `travel_time_matrix`를 요청에 직접 제공했다. 따라서 Google Routes,
`tcache`, 실시간 교통 또는 실제 도로망에서 이동 시간을 생성하는 과정은
검증하지 않았다.

또한 다음 항목은 별도 검증이 필요하다.

- 당일 휴무 및 계절별 운영 시간의 정확성
- 교통 정체, 도로 통제 및 대중교통 시간표 변화
- 해가 없는 일정과 잘못된 입력에 대한 실패 처리
- optional 장소, priority, `order_locked`, `BEST_EFFORT` 정책
- 16개 이상 장소에서 사용하는 휴리스틱 및 대규모 성능

100건은 서로 다른 100명의 원문 일정을 그대로 복제한 것이 아니라, 실제 사용자
여행기에서 추출한 20개 기본 일정에 5가지 제약 변형을 적용한 데이터다. 이동
시간 행렬도 좌표 기반 결정적 추정값이므로 실제 경로 품질의 절대 평가에는
사용하지 않는다.

## 결론

실제 가능한 계획을 모델링한 현재 데이터셋 범위에서는 `troute` 배포 서버가
100% 성공률로 최적해를 반환했다. 따라서 이 데이터셋은 배포 전후의 positive
회귀 테스트와 API·solver 통합 확인에 사용할 수 있다.

실제 여행 가능성까지 보증하려면 공식 운영 시간과 Google Routes 또는
`tcache`가 생성한 날짜·시간별 비대칭 이동 시간 행렬을 추가로 사용해야 한다.
